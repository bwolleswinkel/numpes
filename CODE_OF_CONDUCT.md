# Principles

Below we list the important principles underlining the development of this package.

## Our standards

We strive to write versatile, high-quality, and robust code. This entails that all the functionality we claim to provide should be rigorously tested and verified. 

### Testing policy

Within NumPES we employ test-driven development. This means we write our tests during, or preferably even before we write the underlying functionality we are trying to test.

We also aim to have as few external dependencies as possible, to increase its longevity, and reduce the risk of outdated and version-incompatible code. All dependencies we do have are dependencies on well-established, mature Python projects.

## Attribution

For more information on becoming a contributor, developer, or maintainer of NumPES, see Contributing.

### Use of generative AI

Within NumPES we encourage efficient code design, and we allow the use of generative AI under the conditions and precautions that accompany these tools. The corresponding contributor is always the end responsible person for delivering code up to the quality levels we expect.

Whenever significant parts of functions, methods, or classes have been generated by an LLM, we assign the following attribution comment to the corresponding code:

``` py
# FROM: <tool_name> <model_name_and_version> | YY/MM/DD<[review_status]>
def foo():
    ...
```

Here, `<tool_name>` refers to the tool (e.g., GitHub Copilot, Claude Code, Cursor), `<model_name_and_version>` refers to the name and version of the LLM (e.g., Gemini 3.1 Pro, Claude Sonnet 4, Mistral Large 3 v25.12), and `[review_status]` refers to (a combination of) `untested` or `unverified`. A full example would be:

``` py
# FROM: GitHub Copilot Claude Sonnet 4 | 26/04/15[unverified]
```

In development-ready code, we require that the review status is neither `untested` nor `unverified`.
